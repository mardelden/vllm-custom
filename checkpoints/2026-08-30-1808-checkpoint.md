## Lessons learned

- **`vllm-custom` `main` is a stale baseline** — 1938 commits behind `upstream/main`. The working
  branches are rebased on current upstream, so `main` is the *least* current ref in the repo.
  Never branch new work from it.
- **The plan-108 briefing was wrong on both its fix proposals.** (a) "Compare against the sm100
  sibling, which already serves this model" — that backend gates on
  `qk_nope_head_dim in [128,192]` and GLM-5.3 is **256**, so it rejects the model too. The B200
  path is `FLASHMLA_SPARSE` (`major in [9,10]`), which has no geometry gate. (b) "Unpacked bf16
  looks cheaper" — five layers of fixes end at `TllmGenFmhaRunner: Unsupported architecture`;
  **trtllm-gen has no sm120 build**. Both premises had to be disproven before the real route
  (zero-padding onto the existing packed kernel) became visible.
- **FastSafetensors ships a 16 GiB `max_copy_block_size` default.** Every real shard is smaller,
  so `submit_io` emits one request per shard served by **one thread**, while the 16-thread bounce
  buffer it already allocated sits idle. Generic defect affecting any model with shards < 16 GiB.
- **Dividing by the wrong denominator produced a wrong bottleneck.** I reported the loader at
  2.86 GiB/s (~25% of drive) by dividing by the 83.23 GiB *resident weight delta*. The iterator
  actually moves **153.36 GiB** (each rank sees all tensors via broadcast, keeps its TP shard).
  Real rate 8.46 GiB/s ≈ 75% of ceiling. Instrumentation, not arithmetic, settled it.
- **`cudaMemcpy` is 1.2% of reader-thread time; `pread` is 98.8%.** H2D was never a factor
  (pinned H2D measures 49 GiB/s). `nvidia-smi` reporting PCIe Gen1 is idle power-saving — it
  ramps to Gen5 under load.
- **KV cost per token *falls* with model length** (~21 KB @16k → ~11 @64k → ~9.5 @128k) as block
  rounding and KDA state amortize. Extrapolating 128k from the 16k figure made it look impossible;
  it was comfortable.
- **vLLM's CUDA-graph memory *estimate* over-charges ~0.6 GiB vs ~0.3 GiB real capture.**
  `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` + `--kv-cache-memory-bytes` is what unlocked 128k.
- **`sweep3.py` had two bugs that would silently corrupt a 300 W run**: `wait_full_power()`
  hardcoded 600 W (would burn its 200 s timeout on all 8 configs), and `killall()` matches
  `/proc/*/exe → */uv/python/*` — which the venv interpreter resolves into, so launching the sweep
  under the venv makes it **kill itself**. Must run under system `python3`.
- **`pkill -f "vllm serve"` kills your own ssh session** — the remote command string contains that
  literal text. Use a bracket-escaped pattern (`"vllm[ ]serve"`) or the `/proc/exe` matcher.
- Speculative-decode acceptance rate on ~200–300 drafted tokens is **too noisy to use as a
  correctness gate** (saw 45.2% vs 53.2% vs 66.0% across runs of identical weights). Destination
  digests are the real gate — decision 002 says exactly this.

## Decisions made

**Choice:** Where to record the DeepSeek-V4 patch set, given it targets `jasl/vllm` not our fork.
**Picked:** `plans/004-...md` + `overlays/dsv4-startup/` in `vllm-custom`, on its own branch.
**Why:** Decision 006 gives this repo ownership of source-level release facts regardless of base tree.
**Alternatives considered:** Putting it in the proxmox repo (rejected — that repo owns images and
profiles, not source contracts); minting a `manifest-r1.json` (deferred — a manifest is a release
identity and this is still a candidate).

**Choice:** Which fix shape for GLM-5.3 NoPE on sm120.
**Picked:** Zero-padded RoPE onto the existing packed `fp8_ds_mla` kernel.
**Why:** Zero rope dims contribute nothing to q·k, so the math is unchanged; FlashInfer's sm120
kernel already ships a `_MODEL_TYPE_GLM_NSA` reached via `kv_scale_format="arbitrary_fp32"`, which
vLLM already selects for `model_type glm*`. No CUDA work.
**Alternatives considered:** Unpacked bf16 cache (measured to a hard wall — no sm120 trtllm-gen
build); the DSv4 `d_qk=512` path (kernel exists at 584 B/token but vLLM has **no writer** for that
layout).

**Choice:** Run the 300 W grid with or without the r1 loader optimizations.
**Picked:** With them (added `--load-format fastsafetensors` + the three env vars to `sweep3.py`).
**Why:** The loader changes are read-path only and produce digest-identical weights, so serving
numbers are unaffected — and bind dropped ~200 s → ~90 s per config, halving grid runtime.
**Alternatives considered:** Stock loader to match the documented harness exactly (rejected —
the earlier floating-power partials were being discarded anyway).

**Choice:** dsh `maxTokens` for GLM-5.3 at a 128k window.
**Picked:** Kept the `65536` the user had set.
**Why:** At 131,072 it is a valid half-window; prompt+output share one budget, so 65536 leaves
~65k for prompts. (At the earlier 64k window that same value would have 400'd most prompts.)
**Alternatives considered:** 32000 (more prompt room, less output headroom).

## Open questions / things to revisit

- **The 9.95 s consumer path** in DeepSeek target load (133,660 tensors of destination work,
  ~74 µs each) and a **~11.6 s uninstrumented model-construction phase** are now the largest
  remaining startup costs. Neither is I/O; nothing in our branches addresses them.
- **`VLLM_ENABLE_STARTUP_PLAN=1` is a no-op on the jasl build** — plans are written every boot with
  stable fingerprints but never applied (`maybe_apply_startup_plan` exits at its first guard because
  `kv_cache_memory_bytes` is already non-`None`). Infra lists this as a startup lever; it does
  nothing. Root cause not fully traced.
- **The DeepSeek target overreads `mtp.*`** — 10.12 GiB (6% of read volume) read and discarded
  every boot, because its filter is post-materialization. Not cheaply fixable: the byte-range
  filter needs `all_local=True`, which doubles per-rank reads (measured 36.4 s vs 29.1 s).
- **GLM-5.3 MTP spec decode (`glm5_next_mtp`) is capacity-blocked**, not code-blocked — OOM during
  weight load, 606 MiB short per card. Needs TP=4 or lighter weights.
- Our GLM branch targets `upstream/main`, which **lacks the image's NoPE groundwork**
  (upstream declares `get_supported_head_sizes -> [576]`; the image ships `[512, 576]`). The
  branch adds that, but the two trees have diverged and need reconciling before this is a real
  fork patch.
- Whether to mint `overlays/dsv4-startup/manifest-r1.json` to make that a formal release contract.
