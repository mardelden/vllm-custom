## Lessons learned

- The same application source does not mean a bit-identical runtime. Native used Python 3.11.2,
  a venv plus source overlays on ext4, and accumulated bytecode. Docker used Python 3.11.16, a
  complete package under `site-packages`, overlayfs, and runtime-specific generated artifacts.
- “Docker creation costs 0.1 seconds” describes only daemon/container control-plane work. It must
  not be presented as the total cost of packaging the runtime; the measured end-to-end penalty was
  initially about 11 seconds and remained about 7.5-8 seconds after bytecode compilation.
- Checkpoint I/O is not the remaining problem. Native and Docker page-cold model loading differed
  by only 0.114 seconds, and direct-ext4 Docker model loading matched native closely.
- Build-time bytecode is worthwhile and low-complexity, but it recovered only 29-32% of the
  native/Docker gap. It is not sufficient to justify a release by itself under the user's
  material-improvement threshold.
- Overlayfs materially slows the isolated Python import graph, but most of that work is already
  overlapped with EngineCore startup. Avoiding overlayfs improved one full start by only 0.499
  seconds, so it is not the full root cause.
- An empty FlashInfer workspace requires the release activation `PATH` containing
  `/usr/local/cuda/bin`. An early isolated-cache harness omitted it and failed XQA; the executable
  preflight caught the error. Do not weaken or bypass this gate.
- Native and container Torch/AOT/startup-plan/FlashInfer artifacts must use release-specific cache
  namespaces. Sharing a directory can trigger cross-runtime invalidation and expensive rebuilds.
- The unresolved delay is predominantly before EngineCore begins. Likely areas are Python process
  bootstrap, package/interpreter/dependency layout, early forkserver preload/child initialization,
  filesystem work outside `site-packages`, and process synchronization. These remain hypotheses.
- For Vitrina documents, use the `vitrina` CLI rather than browser access. For historical host CPU,
  RAM, NVMe, and service telemetry, use the SigNoz CLI/API with the read-only OpenBao credential at
  `shared/services/signoz/prod/readonly_api`; never place its value in a checkpoint.

## Decisions made

**Choice:** Who packages and operates patched vLLM releases?

**Picked:** `vllm-custom` owns exact source/package/dependency commits, immutable manifests, tests,
activation, gates, and handoff. The Proxmox fleet owns Dockerfile adaptation, derived image tags and
digests, profiles/services, attestation, canary, promotion, and rollback.

**Why:** The source repository should provide portable facts and validated artifacts; the fleet must
adapt them to its service, secret, mount, and rollback conventions.

**Alternatives considered:** A source-owned production Docker image or unmanaged runtime overlay.
Both were rejected for fleet deployment. The native overlay remains diagnostic only.

**Choice:** What is the immutable release state?

**Picked:** Preserve r2 as the healthy container rollback and r3 as failed/quarantined evidence.
Do not retarget either release. Any changed contract requires r4.

**Why:** r3 failed the declared readiness gate even though functional and loader gates passed.

**Alternatives considered:** Mutating r3 in place or promoting it despite the miss. Both violate the
release contract.

**Choice:** Should bytecode alone become r4?

**Picked:** No. Include build-time bytecode and image-specific cache namespaces in any future r4,
but first find a material fix for the remaining pre-EngineCore delay.

**Why:** Bytecode saved 3.3-3.6 seconds (approximately 10% of Docker readiness), while the user
asked to avoid ongoing complexity for small improvements and the result still missed 20 seconds.

**Alternatives considered:** Publish a packaging-only r4 immediately. Deferred until the larger
remaining gap is understood.

**Choice:** Sleep mode versus persisted startup state?

**Picked:** Persist disk caches and optimize every startup phase; do not depend on sleep mode.

**Why:** The user intends to shut containers down between model switches, so retained process RAM
or sleeping containers do not satisfy the operating model.
